# ECHO — инструкции для Codex

Ты доводишь один этап игры от начала до конца: правки, проверки, коммиты, слияние в `main`, push, зелёный CI и отчёт. После этапа остановись: следующий этап выбирает владелец.

## Сначала прочитай

1. `CLAUDE.md`: карта кода, стиль, ловушки и проверки. Раздел «Как устроена работа» там написан для агентов Claude. Для тебя вместо него действует этот файл.
2. Бриф текущего этапа в `docs/stages/`. Его раздел «Решения» главнее остального текста.
3. Если бриф оставляет вопрос открытым: дизайн-документ `C:\Users\Admin\Desktop\ECHO — дизайн-документ.md`. Он лежит вне репозитория, его только читать.

## Границы

- Работай в рабочем дереве, которое названо в задаче. Основной клон `C:\Users\Admin\Desktop\echo` трогай только для слияния ветки в `main` и push.
- Без прямой просьбы не трогай `.github/`, `ci/` и `export_presets.cfg`. Ничего не скачивай, не ставь плагины и аддоны Godot. Если без этого не обойтись, остановись и напиши, что нужно.
- Не открывай файлы с ключами на рабочем столе (`api keys.txt` и похожие) и не проси ключи.
- Если бриф неоднозначен, выбери разумный вариант по дизайн-документу и отметь его в отчёте. Работу ради вопроса не останавливай.
- Тексты интерфейса и комментарии пиши по-русски. Разделитель «·» в текстах интерфейса не используй: вместо него запятая, новая строка или значения по краям строки.
- Рабочие деревья и ветки после слияния не удаляй, их убирает ведущий.

## Git: правила владельца

- Автор коммитов — владелец, идентичность уже настроена глобально. Не передавай `-c user.name` или `-c user.email` и не меняй `git config`.
- Себя и ИИ нигде не указывай: никаких `Co-authored-by`, никаких упоминаний в теле коммита и в описании PR.
- Сообщения коммитов пиши по-английски, в повелительном наклонении, как в истории (`git log --oneline`). Один коммит — одна законченная мысль, и проверки проходят на каждом.
- Добавляй файлы в коммит поимённо (`git add <файлы>`), а не `git add -A`.

### Даты коммитов

График вкладов GitHub считает по дате автора, поэтому работа раскладывается по дням: **на один календарный день от 7 до 15 коммитов, число на каждый день случайное.**

1. Посчитай, сколько коммитов уже стоит на каждом дне. Считай по всем веткам, потому что рабочие ветки ещё не влиты:
   ```bash
   git log --all --format=%ad --date=short | sort | uniq -c
   ```
2. Норма на 2026-11-13 уже брошена: **11**. Когда день заполнен, возьми следующий день и брось для него новое число: `shuf -i 7-15 -n 1`. Запиши его в отчёт, чтобы следующий исполнитель знал норму.
3. Время внутри дня бери из этого ряда, следующее после последнего уже занятого на этот день: 09:20, 10:15, 11:40, 12:40, 14:05, 15:05, 16:20, 17:30, 18:45, 20:10, 21:25. Если ряд кончился, придумай правдоподобное время между ними. Часовой пояс +0300.
4. Ставь обе переменные сразу, иначе получится «написано тогда-то, закоммичено позже»:
   ```bash
   GIT_AUTHOR_DATE="2026-11-13 12:40:00 +0300" GIT_COMMITTER_DATE="2026-11-13 12:40:00 +0300" git commit -m "..."
   ```
   В PowerShell после коммита удали обе переменные (`Remove-Item Env:GIT_AUTHOR_DATE, Env:GIT_COMMITTER_DATE`), иначе следующий коммит получит ту же дату.

### Слияние и отправка

- Уже отправленные коммиты не переписывай, `push --force` не делай.
- В `main` вливай только перемоткой: `git -C C:/Users/Admin/Desktop/echo merge --ff-only <ветка>`. Если перемотка невозможна, перебазируй неотправленную ветку на `main` с сохранением дат (`git rebase --committer-date-is-author-date main`), прогони проверки заново и потом вливай.
- После push дождись CI: `gh run watch <id> --exit-status`. Если CI красный, чини его в первую очередь.

## Проверки

Гоняй ровно то, что гоняет CI (`.github/workflows/ci.yml`). Команды написаны для Git Bash (`C:\Program Files\Git\bin\bash.exe`). Godot запускай только с ограничением по времени: при ошибке разбора скрипта он виснет навсегда.

```bash
G="/c/Users/Admin/Desktop/Godot_v4.7.2-stable_win64_console.exe"
gdformat --check --line-length 120 . && gdlint .
timeout -k 5 300 "$G" --headless --path . --import
timeout -k 5 400 "$G" --headless --fixed-fps 60 --quit-after 250000 --path . res://tests/smoke.tscn
# в выводе должно быть SMOKE OK и ни одного SCRIPT ERROR
timeout -k 5 400 "$G" --path . --resolution 720x1280 res://tests/shots.tscn -- <папка для PNG вне репозитория>
```

Снимки делаются настоящим рендером, без `--headless`. Любую визуальную правку проверяй снимками и сам смотри PNG. Новая механика получает проверку в дымовом прогоне.

## Ловушки, которых нет в CLAUDE.md

- `gdformat` на Windows пишет CRLF. После форматирования верни LF (`sed -i 's/\r$//' <файл>.gd`), иначе diff показывает изменённым каждый файл.
- Если Godot завис, останови только тот процесс, который запустил ты.
- В дымовом прогоне после первого провала `_expect` функция `_walk_until` выходит сразу, и следующие провалы — каскад. Смотри на первый.
- `tests/smoke.gd` почти упёрся в лимит gdlint в 1000 строк. Новые проверки выноси в отдельный файл, как `tests/smoke_cassettes.gd`.
- Окно снимков на этом мониторе 593×1055, а не 720×1280. Оценивай пропорции и раскладку, а не пиксели.
- Кадр сразу после `_shot()` длинный, потому что сохраняется PNG, и эффекты короче 0.15 с за него сгорают. Перед таким снимком пропусти два `process_frame`. Враги перерисовываются только в физике (`physics_frame`).
- В тестах реклама выключена (`Ads.enabled = false` в `_ready` у smoke и shots). Так и оставь.
- У новых скриптов Godot создаёт файлы `.uid`. Коммить их вместе со скриптом.
